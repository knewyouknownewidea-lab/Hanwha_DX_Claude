# 통합 확인 범위와 회귀 체크리스트

기준 소스는 `Hanwha_DX_Claude`의 `engine-dx-inventory`(main, `82e1fee`)입니다. 원래 재고 화면의 `Workspace.tsx`, 전용 스타일시트 세 개와 MAIN 01 구매 분석 화면을 기반으로 사용합니다. 교체 대상은 부품 형상과 그 ID 연결이며, 모델은 구조 설명용으로 실제 제작 치수가 아닙니다.

MAIN 01의 원본은 이미 빌드된 독립 HTML입니다. 이 파일의 보존은 새로 API를 연결했다는 의미가 아닙니다. LLM 연결 여부는 원래 화면의 연결 상태를 따르며, 정적 로컬 미리보기는 서버 API를 제공하지 않습니다.

## 모델 통합 검증

- 부품 ID는 형상 분류 ID이며, 실제 품목번호·REV·호기 공급 연결과 구분합니다.
- MBS와 베어링 쉘은 별도 객체이고, 배기밸브 조립체와 하위 부품의 구매 단위를 구분합니다.
- 반복 기통의 재질은 독립적으로 제어하며, 한 기통의 강조가 다른 기통에 번지지 않아야 합니다.
- 확인되지 않은 재고는 회색으로 표시하고, 가상 재고·평가에는 SAMPLE 표기를 유지합니다.
- 반투명 외형 뒤 내부 부품을 선택할 수 있어야 합니다.
- 분리·단면은 위치 설명용이며 실제 정비 분해 절차로 표시하지 않습니다.

## 로컬 실행 방법

원래 Vinext 프레임워크와 `package.json`은 유지합니다. 별도의 브라우저 빌드가 동일한 `app/Workspace.tsx`를 직접 사용하며, 브라우저에서만 쓰는 `next/dynamic`을 `React.lazy`로 연결합니다. 화면을 재구현하거나 iframe으로 넣지 않습니다.

```text
node scripts/setup-preview.mjs
npm run preview:build
npm run preview:serve
```

`setup-preview`는 고정 버전의 `package.preview.json`을 사용해 별도 `.preview-runtime`에 설치합니다. 실제 재현 설치에서 74개 의존성 설치를 완료했습니다. 기존 프레임워크 의존성 목록과 pnpm lockfile은 변경하지 않으며 실행 스크립트를 추가했습니다. `npm run static:build`는 형상 내보내기와 동일한 UI 빌드를 실행해 `dist`를 만듭니다.

의존성을 별도 경로에 설치한 경우 `INTEGRATED_NODE_MODULES` 환경 변수에 해당 `node_modules` 절대 경로를 지정할 수 있습니다. 필요한 패키지는 통합 뷰어의 import를 따르며, 빌더에는 `esbuild-wasm` 또는 `esbuild`가 추가로 필요합니다. 기본 검색 위치는 프로젝트의 `node_modules`입니다. 제한된 Windows 환경의 상위 디렉터리 탐색 문제를 피하도록 `esbuild-wasm`을 우선 사용하고, 표준 package exports·browser·ESM 해석은 그대로 유지합니다.

정적 호스팅용 출력이 필요하면 `INTEGRATED_BUILD_DIR=dist`를 설정해 같은 빌드를 실행합니다. 허용하는 출력 폴더명은 `dist`와 `local-dist` 두 개뿐이며, 서버도 같은 환경 변수로 출력 폴더를 선택합니다.

`local-dist`는 로컬 확인용 정적 결과물입니다. `public` 파일을 그대로 복사해 MAIN 01·JSON·GLB 경로를 유지합니다. JSON이나 GLB가 없을 때는 실제 404를 반환하므로, 잘못된 파일 경로를 앱 HTML로 감추지 않습니다.

브라우저의 데스크톱 검증 크기는 1365×1000, 모바일은 너비 390px입니다. 주요 부품·조립체 하위품·MBS·쉘을 독립적으로 선택했고, 실제 캔버스 클릭으로 반투명 주변 뒤의 라이너를 선택했습니다. 현 호기 공급 ID만 강조되고, 상태색·점멸 정지·모션 감소가 작동했습니다. 6기통 64개에서 7기통 74개로 ID 충돌 없이 재구성했으며 GLB 다운로드 후에도 ID를 확인했습니다. 분리·단면에서 통합 MBS와 쉘의 위치를 유지했고, BOM에서 조립체·하위품 및 MBS 중복을 제외했습니다.

기존 공급업체·유형 공용 재고·세부 항목을 확인하는 흐름을 유지합니다. 최신 사용자 요청에 따라 기본값은 새 가상 데이터이며, 가상 모드에서는 호기별 구매 정보를 처음부터 펼칩니다. 미등록 모드도 명시적으로 전환해 회색·null 수량과 빈 협력사 상태를 확인했습니다. 잘못된 JSON과 가상 데이터를 실제 등록으로 위장한 JSON은 기존 상태를 바꾸지 않고 거부했습니다. 올바른 QA 입력 fixture는 미등록 재고·평가를 유지한 채 연결했습니다. 이 입력은 실제 운영 자료가 아닙니다.

전체 결과는 `verification/integrated-browser.json`에 있으며, JavaScript 오류 0개·실패한 자산 요청 0개입니다. `verification/integrated-demo.webm`은 실제 애플리케이션 화면을 캡처한 최신 시연이며 프레임 캡처 속도·길이는 `verification/integrated-video.json`에 기록합니다. 화면 녹화의 부드러움과 실제 점멸 주기 검증은 구분합니다.

## 가상 데이터 프로토타입 추가 검증

`node checks/simulation.mjs`의 11개 검사로 2호기·5협력사·24품목·138개 3D 매핑의 참조 무결성과 모든 시나리오의 데이터 계약을 확인했습니다. 같은 품번 재고를 여러 구매 위치에 중복 배정하지 않으며, 검사 부적합은 한 번만 차감합니다. 조립체 하위품·통합 MBS·문맥 부품은 ID와 연결을 유지하면서 BOM 집계에서 제외합니다.

브라우저에서는 가상 한빛정밀 선택 시 A호기 라이너 6개, B호기 커버 7개만 강조됨을 확인했습니다. 7개 표의 행·열·검색·호기 필터와 키보드 접근, 전체 호기의 매핑에서 7번 라이너 선택 시 B호기로 전환됨을 확인했습니다. A호기 5번 라이너는 기본 입고 예정에서 입고 시 확보로 바뀌고, 지연 시 예정일이 2026-11-05에서 2026-11-19로 바뀝니다. 검사 부적합 시 5번 커버는 확보에서 미확보로 바뀌며 가용재고가 감소합니다. 기본 시나리오로 돌아오면 원본 값으로 복원됩니다. 수량·사유·표 데이터와 뷰어 상태가 함께 바뀌는 것을 실행했습니다.

새 시나리오 캡처는 `integrated-simulation-receipts.png`, `integrated-simulation-delayed.png`, `integrated-simulation-rejected.png`, 표 화면은 `integrated-data-tables.png`입니다. 실제 업체·ERP·거래 자료에 대한 근거 검증은 수행하지 않았습니다. 모든 업무 수치는 사용자 요청에 따라 만든 가상 값입니다.

`verification/integration-provenance.json`으로 기존 스타일시트 3개의 동일성, 앞선 형상 원본 11개의 동일성, 앞선 DOCK UI·구매 데이터 미사용을 확인했습니다. MAIN 01 SHA-256은 `7470ae35b8989711b2138823e88fa08d0f22f8507a7d5e9f9c9837bf91f6ebf9`로 원본과 같습니다. 이 해시 검증은 MAIN 01의 모든 업무 시나리오를 재실행했다는 의미는 아닙니다.

## 남은 검증과 배포 상태

로컬 5179 미리보기는 동작합니다. 비공개 웹 호스팅은 미완료입니다. 이번 환경의 자동 승인 정책(`sandbox_approval=false`)이 Sites 소스 동기화 도구에 Git 입력을 표준입력으로 전달하는 단계를 거부했습니다. 새로 준비한 소스 경로와 도구의 입력 준비 상태를 확인한 뒤 재시도한 결과도 같았습니다. 따라서 배포 완료나 외부 접속 가능한 URL이 있다고 보고하지 않습니다.

UI 검증은 Headless WebGL 소프트웨어 렌더링으로 실행했습니다. 로컬 정적 빌드 성공은 Vinext 전체 빌드, Cloudflare 배포, 서버 인증·API 검증을 뜻하지 않습니다. 실제 제조 치수·품목 적용·재고·계약 사실도 검증하지 않았습니다. 승인된 설계·구매 원천 자료가 추가되어야 운영 적용을 확인할 수 있습니다.
